# Meridian Harness (Visual FoxPro)

A Visual FoxPro application exercising all five Meridian COM services
(`Meridian.ChatService`, `Meridian.AgentService`, `Meridian.EmbeddingService`,
`Meridian.MemoryService`, `Meridian.ImageService`) through `Meridian.Interop.Com`.

## How the forms are built

Visual FoxPro's native form format (`.scx`/`.sct`) is a pair of DBF-based binary database files
-- not something safe to hand-author as text. So instead of writing `.scx` files directly, each
form here is first written as a plain-text `DEFINE CLASS ... AS Form` block in a `.PRG` file
(`frmchat.prg`, `frmagent.prg`, etc.), and **`BUILDFORMS.PRG` turns those into real `.scx` files**
by instantiating each class and calling VFP's own `.SaveAs()` method -- so VFP's own engine does
the actual binary serialization, not a hand-written guess at the format. The result is a genuine,
normal VFP form, fully editable in the Form Designer, same as if you'd built it there by hand.

Getting each `.prg`'s class loaded first matters: `BUILDFORMS.PRG` uses
`SET PROCEDURE TO frmchat.prg ADDITIVE` (one per form file), **not** `DO frmchat.prg`. `DO` only
runs a program's top-level code once and doesn't reliably keep a `DEFINE CLASS` block inside it
resolvable by `CREATEOBJECT` afterward -- that's exactly what `SET PROCEDURE TO ... ADDITIVE` is
for (loading a file's class/procedure definitions and keeping them available for the rest of the
session, `ADDITIVE` so each new `SET PROCEDURE TO` doesn't close the ones already open). If you
ever see "class ... is not defined" when `CREATEOBJECT` tries to build one of these forms, this is
the thing to check first.

## Prerequisites

1. **The Meridian COM bridge must already be registered** on this machine -- see
   `COM-BRIDGE-VM-SETUP.md` and `COM-INTEROP.md` in the main Meridian repo.
2. **The `MERIDIAN_*` environment variables must be set**, and this machine restarted (or VFP
   closed/reopened) after setting them. (You *can* build the forms before this step -- every
   form guards its COM object creation and shows a clear message instead of crashing if the
   bridge isn't ready yet -- but you'll need it set to actually get responses.)
3. Visual FoxPro (9.0 recommended -- this uses `TRY`/`CATCH`, added in VFP 8).

## Running it

1. Copy this folder to `C:\temp\Meridian\VFP`.
2. In the VFP command window:
   ```foxpro
   SET DEFAULT TO C:\temp\Meridian\VFP
   DO MAIN.PRG
   ```
   The first run builds `frmChat.scx`, `frmAgent.scx`, `frmEmbedding.scx`, `frmMemory.scx`,
   `frmImage.scx`, and `frmMenu.scx` automatically (via `BUILDFORMS.PRG`), then opens the
   launcher. Later runs just open the launcher directly.
3. From then on you can also skip `MAIN.PRG` entirely and run `DO FORM frmMenu` directly, or
   open any of the generated `.scx` files in the Form Designer to look at or edit them visually.

To rebuild the forms from scratch after editing a `.prg` (e.g. after changing layout or adding a
field), delete the `.scx`/`.sct`/`.scx` files and re-run `DO BUILDFORMS.PRG`, or `DO MAIN.PRG`
again -- it only (re)builds when `frmMenu.scx` doesn't already exist, so delete it (or all the
`.scx`/`.sct` pairs) first if you want a clean rebuild.

## Layout

```
MAIN.PRG              Entry point -- builds forms on first run, then opens the launcher
BUILDFORMS.PRG         Generator -- turns the .prg class definitions below into real .scx files
frmmenu.prg             Launcher class source -- five buttons, one per capability
frmchat.prg              Stateless chat (Meridian.ChatService)
frmagent.prg             Multi-turn agent session (Meridian.AgentService)
frmembedding.prg         Embeddings + cosine similarity (Meridian.EmbeddingService)
frmmemory.prg            Remember / recall / forget (Meridian.MemoryService)
frmimage.prg             Generate / edit / analyze (Meridian.ImageService)

-- generated by BUILDFORMS.PRG, not included in the zip --
frmMenu.scx / .sct       Real VFP forms, Form-Designer-editable
frmChat.scx / .sct
frmAgent.scx / .sct
frmEmbedding.scx / .sct
frmMemory.scx / .sct
frmImage.scx / .sct
```

## A heads-up on the Images form specifically

Chat, Agent, Embeddings, and Memory all use patterns already proven in this repo --
`Meridian.EmbeddingService.GetEmbedding`/`CosineSimilarity` and
`Meridian.MemoryService.Recall` return SAFEARRAYs that marshal into ordinary VFP arrays (read
with `ALEN()` and 1-based subscripting), which is also how `COM-INTEROP.md`'s own VFP example
handles `Recall`'s `string[]` result.

**The Images form extends that same assumption to `byte[]` (image data)** -- that a SAFEARRAY of
bytes also becomes a VFP array, each element a number 0-255, read/written via the
`ReadBytesFromFile`/`WriteBytesToFile` helpers at the bottom of `frmimage.prg`. This is the
logically consistent behavior and the most likely outcome, but unlike the other four forms, it
has **not been empirically verified** against the real COM bridge the way Chat was. If
Generate/Edit/Analyze throw a type-mismatch or "cannot convert" error where the other four forms
work cleanly, that's the first thing to suspect.

If that happens, the fix is almost certainly in exactly two places -- `WriteBytesToFile` and
`ReadBytesFromFile` at the bottom of `frmimage.prg` -- and likely means VFP is instead returning
a packed binary string (character data, not a numeric array) for a `byte[]`. In that case:
`ReadBytesFromFile` would become a single-line `RETURN FILETOSTR(tcPath)` (skip the per-byte loop
entirely), `WriteBytesToFile` would become `STRTOFILE(tcBytes, tcPath)`, and every call site that
currently treats the value as an array (`ALEN(...)`, `[lnI]` subscripting) would need to drop
that and treat it as a plain string instead. If you change `frmimage.prg`, re-run
`BUILDFORMS.PRG` (after deleting the old `frmImage.scx`/`.sct`) to regenerate the form.

## Known simplification

Edit uses a fixed 1024x1024 output size (no width/height fields in the UI) to keep the form
layout manageable -- edit `frmimage.prg`'s `cmdEdit.Click` if you want those configurable, the
same way Generate's are, then rebuild.

## If a form fails to create its Meridian COM object

Every form's `Init` wraps `CREATEOBJECT("Meridian.XxxService")` in `TRY`/`CATCH`, so a missing or
unregistered COM bridge doesn't crash the form -- clicking any button shows a clear
"...could not be created: <error>" message instead. If you see that, re-check the COM bridge
registration steps in the main repo's `COM-BRIDGE-VM-SETUP.md`.
